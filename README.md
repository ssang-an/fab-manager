# Fab Manager

Prototype workspace for visualizing dual-fab lot movement, process WIP, equipment queues, and event-timeline playback.

## Equipment, sample lots, holds and forecasting

The 1,800-lot fixture now contains 1,620 MAIN and 180 SAMPLE lots. Each lot has positive `WF_QTY` (MAIN: 10–25, SAMPLE: 1–5), synthetic `equipmentByStep` assignments, and hold-reason records. SAMPLE lots link to a MAIN lot in the same fab and route; these links do not represent verified quality results or enforce release. Square markers distinguish SAMPLE from MAIN dots. Lot details expose related lots, quantity, current status and time-normalized JOB statistics.

Equipment search highlights only JOB START/PROC operations assigned to the matching equipment at the selected time, not every eligible operation. Rankings switch between process WIP, assigned equipment WIP and HOLD concentration. Traveling/OUT lots are excluded from equipment queues. Equipment and hold analytics honor the existing fab/route/lot filters; equipment search is an overlay, not a lot filter. Red H-count rings identify operations holding at least two lots. Suggestions are transparent reason-based review rules, not automatic hold release, recipe changes or equipment switching.

`node scripts/generate_graph_data.mjs` persists `data/job_timing.json` (92,121 completed JOB pairs) and enriched `data/graph_demo.json`. JOB timing pairs start/end at the same lot/path occurrence, excludes interrupted or incomplete pairs and invalid quantities, and records `(JOB END - JOB START) * 60 / WF_QTY`. This is normalized elapsed lot time, **not measured individual-wafer residence time**. Median/P90/weighted means are separated by equipment, operation description and MAIN/SAMPLE. Quantities are constant per lot in this demo; production integration must capture quantity and equipment at JOB time and account for split/scrap/batch/recipe versions.

The timeline spans seven observed days and seven simulated future days. FORECAST labels, an amber map border and a split timeline distinguish the prediction region. A deterministic FCFS event scheduler consumes the current WIP using eligible READY primary tools, with median seconds/WF times lot quantity. <5 samples is labeled low confidence; absent history uses an explicit 60 sec/WF assumption. 20% faster / 25% slower duration scenarios are sensitivity cases, **not statistical confidence intervals**. Current holds default to a simulated release three hours after their original hold timestamp (already-overdue holds release just after the cutoff). This is a fixed-duration approximation to a mean target, not an inferred distribution or operational approval. Released lots queue at the same operation and restart its full job. Completed lots remain completed; no new arrivals, new holds, failure events or backup activation are modeled.

The old randomized history was not resource constrained. To avoid falsely presenting its concurrency as physical single-tool behavior, each demo equipment record explicitly contains `demoSlots`, set to its observed peak concurrent jobs (including running jobs at the cutoff). The scheduler obeys these **virtual** slots; they are not real chamber/batch capacity. Production use requires capacity, availability/PM calendars, arrivals, queue-time limits, hold reasons and release approvals, recipe-specific cycle models, sample-result dependencies and validation against held-out actual outcomes. No forecast accuracy claim is made.

The first sample data set is in [`data/README.md`](data/README.md). It is entirely fictional and exists only for UI development.

## Run the prototype

Use Node.js 22 or newer. No package installation is required.

```sh
npm start
```

Open http://127.0.0.1:4173. Run `npm test` for CSV parsing, replay boundary, and data mapping checks.

The current UI is a full-viewport Canvas route graph with wheel zoom, pointer pan, touch pinch, keyboard navigation, route/Fab/lot filters, and a seven-day event replay. Switch between 2D process flow and a perspective 3D projection. Operations are arranged on seven conceptual area layers: PHOTO, ETCH, DIFF, THINFILM, CMP, CLEAN and MI. In the demo mapping PHOTO/ETCH/CMP retain their names, IMPL and RTP map to DIFF, CVD to THINFILM, WET to CLEAN and MET inspection to MI. Treatment alternatives map to DIFF; merge/exit waypoints inherit the preceding area. All nodes in one area share a depth. Bounded lateral offsets and gentle drift introduce diagonal transfers without changing process order; 2D keeps the wider layout while 3D remains compact. This synthetic mapping is not a verified production area assignment. Camera yaw and pitch are unrestricted. These coordinates demonstrate topology rather than a physical fab floor plan.

The graph reads `data/graph_demo.json` version 3. Regenerate it with `node scripts/generate_graph_data.mjs`. Its deterministic fixture contains 24 routes (23–90 steps on a realized path), 120 lot codes, 1,800 lots, 1,601 operation nodes, 1,776 links, 48 equipment records and 467,550 events. Routes have different entry and exit stages, including intermediate entry and exit. Alternative branches split and rejoin; shared inspection nodes connect groups of routes. A lot chooses one branch per alternative. Physical lot splitting, full production genealogy, rework cycles, actual equipment dispatch and live MES integration are not implemented. Sample-to-main demo links and simulated dispatch are described above.

Events are `[minute_since_start, path_index, status_index]`, with status indices defined by the JSON `statuses` list. MOVE (index 6) additionally includes a fourth field, `arrival_minute`, so a transfer crossing the observation boundary is represented accurately. The observation window is September 4–11, 2026, 09:00 KST. At a selected time, replay uses the most recent event at or before that time. Before the first event, a lot is unreleased. Completed lots count toward OUT and leave the active graph, except selected comparison markers. WIP + OUT + unreleased equals the filtered lot total. WIP includes MOVE, while operation rankings exclude traveling lots and assign them to the destination only after arrival.

Transfers last 8–24 simulated minutes. Playback defaults to 5 simulated minutes per second, making a transfer visible for approximately 1.6–4.8 seconds. Cubic paths are interpolated in world coordinates before 3D projection. Dots settle at their destination and retract toward the departure node before transfer, with stable per-lot offsets and a short travel trail. Fast time scrubbing selects the requested observation directly rather than manufacturing a transfer between unrelated snapshots. Playback continues from the selected observation into the explicitly marked forecast interval; starting at the forecast end restarts at the observation cutoff. Synthetic long queues concentrate on shared gates in metal-1 in Fab A and LDD in Fab B.

Controls: wheel or +/- to zoom, F to fit, Escape to close details. In 2D, drag pans. In 3D, plain drag also pans; hold Shift while dragging with the primary mouse button to rotate. Right-button drag pans. Ctrl/Cmd+click remains reserved for lot comparison. Search a lot code or ID and select a result to locate it. Selecting a lot highlights its actual branch choices. Multi-select mode or Ctrl/Cmd+click adds/removes a lot from comparison (up to six). Comparison can also be selected through a lot inspector or a checkbox in the operation popup. Each comparison path has its own color; shared edges use alternating dashes. "전체 맵에서 비교" clears route, fab and search filters while preserving selected lots.

The sidebar's top-five WIP ranking and operation popups update with playback time and current filters. Map labels identify crowded operations; click a label, operation marker or ranking entry to open its popup. Popups list primary and backup equipment by fab, readiness (including PM), and separate wait, processing and hold/end lot lists. Equipment eligibility/readiness is a synthetic static mapping; no dispatch or backup activation occurs. Exit markers have no processing equipment.

The original three CSV fixtures are retained for reference and are no longer the graph's data source. In those CSVs, `base_plan.lot_code` is a route label and event `lot_code` values identify individual sample lots. The new graph explicitly maps each lot code to a route and each lot to its realized path, with stable operation occurrence IDs. Production integration should retain route/version and occurrence keys rather than joining descriptions.

### Equipment DOWN / maintenance demo

Hold controls in FAB INSIGHTS compare 1/3/6/12 hours, a custom 0–168 hour target, and a no-release baseline while keeping processing-time assumptions and equipment state constant. Metrics are additional completions after LIVE at +1/+7 days, +7-day WIP and cumulative forecast HOLD lot-hours. The suggested comparison winner maximizes +1-day completions then minimizes hold exposure; it is not a cost/quality-optimized production policy. Select a comparison target to update the map or use +3-hour preview. Historical analytics group by operation occurrence and hold code, reporting episode count, distinct affected visits / all visits, observed occurrence days and accrued lot-hours including open holds. Forecast events are excluded. AHSO means Auto Hold Spec Out (user-confirmed): a spec-out automatic hold. Its occurrences on MET steps are synthetic. Insight prompts request measured values, specification limits, recurrent out-of-spec items and upstream equipment review; no measured values or specification limits are fabricated. New recurrent holds are analyzed historically, not injected into forecasts.

The AREA dashboard shows all equipment outages; impact lot counts follow the current lot/FAB/route filters. Click an equipment entry to inspect its alarm, owner, restoration status, time-filtered maintenance history, affected operations and lots. Amber map squares identify operations with a waiting queue assigned to DOWN equipment or explicitly interrupted jobs; large queues also have DOWN labels. Unrelated holds are not attributed to equipment failure.

Equipment readiness now uses time-indexed maintenance intervals (`equipment-health.js`), not only the static baseline availability. The synthetic A-ETCH-1, B-CVD-1 and A-MET-1 failures start exactly at the latest observation boundary (minute 10080). In-process jobs become EQP holds with an explicit `downCause`; earlier observations are unchanged. Each has a prior completed maintenance record before the history window. Backup tools have sample PM histories. All records are fictional, not live maintenance feeds.

Simulation excludes DOWN/PM tools until their seeded synthetic recovery estimates: default DOWN uniform 12–36h (mean 24h), COPM scheduled PM 4–12h, placeholder NPM_RF 24–72h and NPM_STAGE 12–48h. Code ranges are demo assumptions, not learned engineering estimates. Inform notes are retained for future AI estimation; no AI analysis is connected. Values are deterministic across replay and hold comparisons. Actual incident end/approval records remain unchanged; predicted READY only applies beyond the observation cutoff. Held lots release under the selected timing scenario (default 3h, or no-release baseline); hold release and predicted equipment recovery are separate clocks. Waiting lots may use other READY qualified primary tools under the existing scheduler. Backup activation, repair completion and post-maintenance qualification require external confirmation and are not automated. Maintenance suggestions are review prompts, not executable repair instructions.
